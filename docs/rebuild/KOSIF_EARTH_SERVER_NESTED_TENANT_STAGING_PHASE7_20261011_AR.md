## ما تم إصلاحه بالفعل على الخادم

أضيف التحقق `validateEngagementTenantState()` في `cloudflare/tenant-guard.js` لضمان أن البيانات المتداخلة داخل حالة ملف المراجعة لا تحمل معرف `companyId` أو `workspaceId` لشركة أو مساحة أخرى. الطبقة الحالية في `engagement-api.js` تتحقق من الجذر **وكذلك** العناصر المتداخلة:

1. **PUT الحالة**: يرفض طلب العميل إذا كان مستند/قضية/PBC يحمل معرّف شركة أجنبية أو علامة ملكية غير صالحة، أو مفاتيح `__proto__` أو `constructor` أو `prototype`. يتم الرفض **قبل** أي كتابة D1 أو زيادة الإصدار أو تسجيل حدث حفظ.
2. **GET الحالة**: يرفض إرجاع حالة قديمة في D1 تحتوي علامات ملكية أجنبية متداخلة ويرجع `409 stored_state_tenant_scope_invalid` دون إظهار محتواها. لا تُمسح تلك الحالة أو تُنسب للشركة المفتوحة تلقائيًا.
3. **توقيع ومعاينة نسخة ملف المراجعة**: يستعمل `engagement-backup.js` التحقق نفسه ويمنع توقيع ملف قديم ملوث بعلامة مالك `null` أو مفاتيح غير آمنة، حتى لو كان جذر ملف المراجعة صحيحًا.
4. التحقق من هوية JWT وربط المستخدم/الشركة/المساحة في D1 وتوقيع HMAC يستمر من العمل السابق. لا يوجد مُنفّذ لاستعادة شركة فعلية، ولا تخويل AI لإصدار اعتماد.

## حاجز جاهزية Staging الجديد

الملف `scripts/tenant-staging-release-gate.mjs` هو فحص **نصي فقط**، لا يقرأ قيمة سرّ، ولا ينشئ موردًا ولا يرفع Worker. تشغيله على `cloudflare/wrangler.toml` الحالي أعاد **exit 2** و`readyForOfflineReview:false` مع **7 مانعات**: لا إعداد `env.staging` منفصل، ولا تفعيل `strict` فيه، ولا `issuer/audience`، ولا allowlist خاصة للـOrigin، ولا ربط واضح بمعرف D1 محدد واسم R2 bucket محدد لبيئة Staging.

حتى على تهيئة يجيزها الفحص النصي ستبقى `liveDeploymentAuthorized:false`؛ لأنه لا يمكن إثبات مصدر JWT أو تنفيذ D1 migration أو ملكية R2 أو صلاحيات مدير ومراجعَين من ملف TOML فقط.

## فحص حساب Cloudflare المتصل — قراءة فقط

تم استخدام اتصال Cloudflare المخوّل للاستعلام **دون أي كتابة أو طلب أسرار**. الاستعلام عن فهرس الموارد أعاد **8 قواعد D1 و4 حاويات R2** في الحساب المتصل، ووجود Worker باسم `kosif-audit-realtime`. بعض الموارد تحمل أسماء خاصة بوحدات SEE/KOSIF القديمة. **لا يجوز استنتاج أن تلك الموارد تتبع بيئة Staging أو استخدامها تلقائيًا للمراجعة**.

واجهة `script-settings` لم تُرجع في الحقول المعروضة دليلًا كافيًا على ربط Worker بـ`KOSIF_DB` و`KOSIF_DOCUMENTS` أو تفعيل `KOSIF_TENANCY_MODE=strict` في النسخة المنشورة؛ **لذلك لم يُثبت التشغيل الحي**. لم تتم قراءة محتويات D1 أو ملفات R2 أو مفاتيح أو إعدادات سرّية، ولم يتم إنشاء موارد أو نشر أو تغيير إعداد.

## ما لا يزال ممنوعًا (P0)

- لا `restore/commit` لشركة أو جهاز، ولا تشغيل نقل الجهاز الشامل في EARTH؛ ملف تصدير الشركة المحلي ما زال `restorable:false`.
- لا استعمال لقواعد D1 أو R2 القديمة الخاصة بمشروع آخر لمجرد تشابه الاسم.
- لا يمكن إثبات استعادة A/B على Staging قبل توفير مصدر هوية موثوق وبيئة منعزلة وقاعدة D1 وR2 مثبتتين واختبارات أصلية لسجلات كل شركة ومرفقاتها.
- لا موافقة بشرية مزدوجة، ولا مصدر ملكية مضمون للسجلات القديمة مجهولة المالك في الحسابات أو المخزون أو المشتريات، ولا استعادة كاملة مع `rollback` معتمد.

## الاستكمال القادم

تعريف Staging مستقل بخطة أسماء موارد ومصدر هوية موثوق **دون تسجيل الأسرار في Git أو المحادثة**، ثم اختبار قراءة/حفظ/توقيع/معاينة ملفين لشركتين على D1 وR2 حقيقيين، مع أدلة HTTP ونسخة/تراجع وعدم تسرب أي سجل أو مرفق. لا تنقل مرحلة الإعداد لتصبح نشرًا إنتاجيًا إلا بعد مراجعة صاحب الصلاحية وإغلاق كل مانع.
